# 碰撞与战斗调用流程

## 文件职责

| 文件 | 唯一职责 |
| --- | --- |
| main.gd | 页面、场景选择/重开、状态显示、桌面窗口适配 |
| demo_scenario.gd | 创建一局、注入战斗回调、调度固定时间步 |
| ball_factory.gd | 从配置创建满血球、复制攻击防御、关联独立技能记录、生成出生状态 |
| ball_config.gd / default_ball.tres | 球的配置结构与默认值 |
| ball.gd | 单颗球的运行数据；没有执行逻辑 |
| ball_skill_state.gd | 每个球独立的技能关联和 runtime，配置资源可共享 |
| ball_temporary_state.gd | 临时状态数据，目前没有效果执行器 |
| collision_event.gd | 检测、物理和战斗共用的事件记录 |
| arena.gd | 运动、检测、位置纠正、组织求解、检查并统一提交状态、发通知 |
| collision_solver.gd | 只计算候选速度和受冲量影响的接触索引 |
| impact_skill_config.gd / default_impact_skill.tres | 撞击参数的结构与默认值 |
| impact_skill.gd | 单向撞击伤害公式，不扣血、不检测碰撞 |
| combat_system.gd | 按技能计算并汇总同刻伤害，返回候选生命和死亡名单 |
| combat_result.gd | 候选生命与死亡名单，不执行修改 |
| ball_validation.gd | 只读输入、配置和候选结果校验 |
| ball_renderer.gd | 读取位置、半径和生命，绘制球及血条，管理展示颜色 |

脚本位于 `demo/scripts/`，资源位于 `demo/configs/`。场景文件声明节点、球数及配置；`project.godot` 管理启动与窗口设置；`scripts/run_regression.py` 组织测试。Arena 不再保留工厂初始化和校验的转发入口。

## 启动

```text
project.godot → main.tscn → Main._ready()
→ select_scenario() → 实例化 balls_*.tscn
→ DemoScenario._ready()
→ 创建 CombatSystem，arena.combat_resolver = combat_system.resolve
→ 创建 BallRenderer，绑定 arena.balls
→ BallFactory.create_demo() 创建球并初始化战斗与运动数据
→ 注册球，设置配色，1× 运行
```

新建球从 BallConfig 复制 max_health、attack、defense、radius、mass，current_health 初始化为 max_health。配置的 impact_skill 为空时不装备技能，否则创建独立 BallSkillState，skill_id 为 impact。已有球的 initialize_demo / initialize_positions 只重新生成运动状态，不重置生命、技能或 Arena 计数。完整重开通过 Main 重新实例化场景。

## 每个碰撞时刻

```text
DemoScenario._process → advance_real_time → Arena.step(1/120)
→ _next_event 预测最早事件，创建 CollisionEvent
→ 球移动到接触时刻
→ _contacts_at_event 复用预测事件、补齐法线和碰前速度、扩展接触链
→ CollisionSolver.resolve 计算候选速度和受冲量接触
→ Arena 标记 confirmed，调用注入的 combat_resolver
→ CombatSystem.resolve → ImpactSkill.damage → CombatResult
→ Arena 检查速度和生命候选结果
→ 一次提交速度、生命，移除死亡球
→ 原碰撞通知及 combat_committed 通知
→ 用剩余球预测本步下一次碰撞
```

没有新增第二套碰撞检测。CollisionEvent.a/b 是物理求解中的临时下标，ball_a/ball_b 是跨移除仍有效的引用；b=-1、ball_b=null 表示墙。normal 沿用物理约定，从 b 指向 a；攻击方向 A→B 必须取 -normal。time 为当前剩余时间段内的预测时间，不是全局时间戳。

预测记录没有最终球间法线；移动到接触时刻后才补齐。静止接触链可能增加事件，但同一个种子事件会原对象复用。只向战斗层提供求解成功且实际受正冲量的事件。墙事件、未确认事件不会造成伤害。

## 伤害公式

方向 n 从攻击者指向防守者，vA/vB 都取碰前快照：

```text
接近速度 = max(0, dot(vA-vB, n))
有效速度 = min(max(0, dot(vA, n)), 接近速度)
伤害 = 攻击 × (质量 / 基准质量) × (有效速度 / 基准速度)²
       / (1 + 对方防御 / 防御系数)
```

默认基准质量 1、基准速度 200、防御系数 100。质量 1、攻击 10、有效速度 200、目标防御 0 时伤害为 10；防御 100 时伤害为 5。擦边只按法向分量计算；静止球不反击；追赶按速度差限制。生命使用浮点值，不取整，无额外最小伤害或伤害上限。

同刻事件全部读取提交前的生命，伤害按目标汇总并以固定数值顺序累加，最后一次扣血，允许同归于尽。接触链中原本静止的球可能传递物理冲量，但不会凭空获得碰前主动撞击速度。当前所有球都可以互相伤害，没有阵营过滤、胜负判定、经验或掉落。

## 提交和失败边界

CollisionSolver、ImpactSkill 和 CombatSystem 不修改 Ball。CombatResult 通过检查后，Arena 连续写回速度、生命并移除死亡球，中间不调用外部代码。之后的监听者只能观察到完整结果。

若物理求解或战斗候选结果无效，本批速度与生命均不提交，也不发成功通知；记录错误，场景暂停。已经推进到接触点的位置和时间保留，不做整步回滚。combat_failures 单独统计战斗失败。

combat_resolver 是内部可信的纯计算接口，不能在回调中主动改球或列表。通知监听者同样不应在回调中随意改变物理状态。未注入回调时 Arena 保持纯物理模式；没有配置生命的裸 Ball 也不参与战斗。

## 显示和使用

桌面启动采用当前屏幕可用区域约 85% 的普通窗口，居中、可拖动缩放。横屏按钮紧凑排列，竞技场等比显示。血条显示当前生命比例，状态栏显示存活球数。Restart 用原种子创建新球并恢复满血。

## 验证入口

从仓库根目录运行 `python scripts/run_regression.py`，可用 GODOT_BIN 指定 Godot。测试包括原有物理随机对照、长期守恒、布局，以及技能公式、候选结果不修改状态、事件对象复用、同刻互伤/死亡、失败原子性、墙/分离接触不扣血、重开恢复、100 球战斗推进。守恒测试关闭战斗回调，避免死亡球移除改变统计系统的总能量。
